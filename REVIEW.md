# Review instructions

What to flag in a pull request here, at what severity, and what to leave alone. Project
conventions are in `AGENTS.md`. This file is self-contained: the review agents read it as
text and do not follow references out of it, so every rule they enforce is stated here.

## What Important means

Reserve Important for a finding that would corrupt data, lose a user's files, or break
sync between two devices:

- A file, version, or tag that can be lost, orphaned, or resurrected after deletion.
- Two devices converging on different state, or a hash that differs across devices for
  the same source file.
- An upload or import that silently drops items, double-counts them, or reports success
  without the bytes landing.
- A migration that isn't backward compatible with an installed app, or a write outside a
  transaction that needs one.
- Blocking the JS thread on a path the user waits on, including any synchronous
  `expo-file-system` call.
- A secret, app key, recovery phrase, or file path reaching a log line or error message.
- A comment stating a wrong field list, state set, count, or returned shape. A reader
  trusts it over the code.

Naming, structure, refactoring suggestions, and test organization are Nit at most.

## Always check

The rules this repo keeps breaking. Flag every new violation.

- **Facade boundary.** App, service, manager, or hook code calling `ops.*` or the SDK
  instead of `app.*`. SQL outside `packages/core/src/db/`.
- **Missing integration test.** A change to upload, download, sync, import, trash, or
  delete behavior in `packages/core` with no test under `apps/integration/test/`. Unit
  tests do not cover two devices disagreeing.
- **Duplicated implementation.** A new function, method, or adapter entry whose body
  substantially repeats one already in the same file or module. Name the existing one and
  say what differs. Two near-identical implementations drift, and the older one usually
  carries the tests.
- **Integration tests that fake the app.** Creating files with `app.sdk.injectObject()`
  instead of `addFiles()`, writing `trashedAt` or `deletedAt` directly instead of calling
  `app.files.*`, or forcing a sync tick instead of waiting with `waitForCondition()`.
  These pass while the real path stays broken.
- **Database query changes.** A new or edited statement under `packages/core/src/db/`, or
  a change to what a query filters, joins, or orders by. Ask for benchmark numbers:
  `bun --cwd apps/benchmark bench` captures the statements the ops actually issue and
  runs `EXPLAIN QUERY PLAN` on each, so it shows whether the change still hits an index.
  Flag any filter or sort added on an unindexed column.
- **Blocking filesystem calls.** `File.info()`, `File.delete()`, `Directory.info()`,
  `.create()`, `.list()` on a production path. `react-native-fs` is required.
- **Committed shell scripts.** Any new `.sh` outside `apps/cli/install.sh` and
  `test/fixtures/`.
- **Inexact dependency versions.** `^` or `~` in `dependencies` or `devDependencies`.
  `peerDependencies` may use ranges.
- **Native platform directories.** Files added under `apps/mobile/ios/` or
  `apps/mobile/android/`. Both are generated by `expo prebuild` and gitignored.

## Writing

Prose defects are findings, not decoration. No em-dashes and no arrows in any category
below.

**Comments.** These apply to code comments only. Do not carry them over to a changeset,
a PR description, or a commit body, which have their own rules below. Flag a comment
that:

- Restates the line beneath it or paraphrases the signature.
- Narrates the change rather than the state: "now uses X", "no longer Y", "previously".
  A migration or compatibility shim is the exception.
- Justifies ordinary structure: "a helper so call sites don't drift", "DRY", "single
  source of truth".
- Is a section divider or says "defense in depth".
- Points at a file, spec, plan, or PR the reader cannot open.
- Pads: a setup sentence ("This is important because", "The reason for this is"), a
  restatement of the sentence before it, or a filler opener ("Note that", "Here we", "In
  order to", "For clarity").
- Retells control flow: "first we load the rows, then we filter".
- Hedges where the code is definite: "might", "could", "may want to".
- Reaches for a technical word where a plain one exists, or builds a noun out of a verb
  ("performs validation of" for "validates").
- Cites a measurement: a benchmark number, a profile percentage, a device timing. It was
  true once under conditions the file does not record. Ask for the mechanism.
- Runs long: over two lines inline, or over six for a header, without a constraint that
  needs the room. Say which sentences to cut.

Flag the absence too: an ordering constraint, race, or platform workaround introduced
with nothing explaining why, and a genuine-why comment the diff deletes whose reason
still holds.

**Commit messages.** Flag a subject naming the mechanism instead of the effect, a body
describing how the branch got here instead of what the code now does, a body past two
short paragraphs, one bullet per file, or a body not wrapped near 76 columns.

**PR descriptions.** Flag one that opens with the mechanism instead of what someone using
the app would have seen, runs past three or four sentences without separate changes to
justify bullets, uses a term specific to this codebase without saying what it is, leans
on context the reader lacks (another PR, a plan file, a prior conversation), claims a
behavior the diff does not contain, walks the diff file by file, or is hard-wrapped.

**Changesets.** CI checks the frontmatter key, so review the copy. Flag a description
that names the mechanism instead of the outcome, bullet-lists one line per package,
repeats the commit subject verbatim, or carries `Closes` on a PR that is not last in its
stack. "Now" is correct here: a changelog reads against the previous release, so
"Downloads now check for free space" is not edit-history narration. An app entry says
what a user sees or can now do; a library entry says what a
caller must change. Also flag the miss: a user-facing change to `mobile`, `web`,
`desktop`, or `cli`, or an API change in `core` or `logger`, shipping with no changeset.

**All prose, including markdown and test names.** Flag an aphorism where a fact belongs,
the "not just X, it's Y" pivot, a rule of three, over-bolding, and any of: load-bearing,
delve, leverage, utilize, robust, seamless, crucial, pivotal, paramount, realm,
underscore, foster, elevate, unlock, streamline, ensure, boast, navigate, landscape,
holistic, bespoke, groundbreaking, testament, synergy, endeavor, meticulous, nuanced,
notably, importantly, essentially, effectively, simply, basically, additionally,
furthermore, moreover, comprehensive, myriad, plethora, facilitate, elegant, or "pins" as
a verb for anything but a dependency version. A test name must state the behavior in
plain words and match what it asserts.

## Do not report

- Anything CI enforces: `oxlint`, `oxfmt`, `tsc`, `knip`, `cargo fmt`, `cargo clippy`.
- Formatting, import order, line length.
- Suggestions to extract a helper, rename for consistency, or add an abstraction, when
  the code is correct and nothing in the file already does that job.
- Generated files, lockfiles, and `apps/mobile/e2e/assets/`.

## Verification bar

A behavior claim needs a `file:line` citation, not an inference from a name. If you
cannot point at the line that makes the finding true, do not post it. For a race or
ordering bug, name the two operations and the interleaving that breaks; "this could race"
without an interleaving is not a finding.

Attribute every finding to its rule as `REVIEW.md > Always check > Facade boundary`, and
quote the clause. A finding you cannot attribute is a general observation, so label it as
one rather than implying it carries repo policy.

## Reporting

Report every finding, tagged by severity. Do not cap nits, drop findings to keep a review
short, or withhold findings on a re-review because an earlier round posted some. The
severity tag and the summary tally are what make a long review readable.

Open the review body with a one-line tally, for example `1 important, 3 nits`. When
nothing Important was found, say "No blocking issues" first. Write the summary for
someone who has not read the diff: lead with what is wrong, in product terms, before any
mechanism.
